# Kuadrant Rate Limiting (concept)

Why and when to use Kuadrant's [[kuadrant-ratelimitpolicy]] CRD (request-count-based), before its field-level reference. For token-count-based limiting (LLM-relevant), see [[kuadrant-token-rate-limiting-overview]] instead. (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L14-22)

## What a RateLimitPolicy does

Targets `HTTPRoute`/`GRPCRoute`/`Gateway` resources (optionally a subset via `sectionName`), abstracting the underlying Envoy Rate Limit Service protocol and its configuration surface. Cluster operators can set defaults that hold until a more specific policy applies. (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L14-22)

Enforcement flow: gateway checks matching rules on an incoming request → sends an Envoy RLS `RateLimitRequest` to **Limitador** → Limitador responds `OK` or `OVER_LIMIT`. (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L23-34)

## Targeting patterns

- **Route-targeted**: enforced on all traffic matched by the route, across every Gateway in its `parentRefs`. (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L65-77)
- **Gateway-targeted `defaults`**: protects the whole gateway except where a more specific route policy exists; auto-covers new routes. (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L94-106)
- **Gateway-targeted `overrides`**: wins over every route-level policy unconditionally. (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L122-159)
- **Hostname specificity**: most-specific-hostname-wins when policies aren't merged (no overrides in play). (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L78-84)

A worked example with 4 policies across 3 routes and 1 gateway (both the `defaults` and `overrides` variants) is in the reference/component page — see [[kuadrant-ratelimitpolicy]]. (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L122-159)

## Limit anatomy

A limit is one or more `rates` (limit + window), optionally scoped by `counters` (CEL-expression qualifiers — one counter per distinct resolved value, e.g. per username) and gated by `when` predicates (all must be true to activate). Selectors in `when`/`counters` are a subset of Kuadrant's [Well-known Attributes](https://github.com/Kuadrant/architecture/blob/main/rfcs/0002-well-known-attributes.md) ([RFC 0002](https://github.com/Kuadrant/architecture/blob/main/rfcs/0002-well-known-attributes.md)). (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L160-216)

## Why Kuadrant doesn't use Envoy's native Rate Limit filter

Two Istio/Gateway API limitations motivate this: (1) only one filter chain per listener means one shared rate-limit "domain" for everything unless something adds multi-domain support; (2) fine-grained per-route-rule descriptors require Envoy "named routes," but Gateway API HTTPRoute rules have no stable name and Istio's internal VirtualService route names are auto-generated/not user-referable. Kuadrant's answer is a wasm-shim (an Istio `WasmPlugin`, auto-generated by the Kuadrant control plane) that implements the RLS protocol directly against Limitador — giving multiple isolated rate-limit domains per gateway and HTTP-route-rule-level matching. (raw/kuadrant-operator/doc/overviews/rate-limiting.md#L232-327)

## Known limitations

- Same-namespace targeting only.
- No mixed HTTPRoute/GRPCRoute on one Gateway hostname.

(raw/kuadrant-operator/doc/overviews/rate-limiting.md#L227-231)
