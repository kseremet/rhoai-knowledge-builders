# Installing the Red Hat OpenShift AI Operator

Installs the [[rhoai-operator]] itself — the first of the high-level
install tasks (requirements → **operator** → components → user groups →
dashboard access). Component installation is a separate step: see
[[installing-rhoai-components]].

## Preconditions

**Subscriptions / access**

- A Red Hat OpenShift AI Self-Managed subscription (plus a platform
  subscription if installing on a Red Hat-managed cloud environment).
- Cluster administrator access — the `kubeadmin` user is not allowed; you
  must be a user with the `cluster-admin` role.
- OpenShift CLI (`oc`) installed.

**Cluster**

- Supported OpenShift version: OCP 4.19–4.20 (4.20+ required for Distributed
  Inference with llm-d), OpenShift Dedicated 4, ROSA classic 4, ROSA HCP 4,
  or OKE (OKE requires a Red Hat licensing exception for the dependency
  Operators it needs — GAP: exact list/process not detailed further in this
  guide beyond naming the dependent Operators).
- A minimum of 2 worker nodes, ≥8 CPUs and ≥32 GiB RAM each (single-node
  OpenShift: ≥32 CPUs and ≥128 GiB RAM on that one node). More may be needed
  depending on workload.
- A default storage class supporting dynamic provisioning
  (`oc get storageclass` to confirm).
- An identity provider configured (RHOAI relies on cluster auth).
- Open Data Hub must **not** already be installed on the cluster.
- Internet access to `cdn.redhat.com`, `subscription.rhn.redhat.com`,
  `registry.access.redhat.com`, `registry.redhat.io`, `quay.io` (plus NVIDIA
  NGC domains only if you build/pull custom CUDA images directly from
  NVIDIA).
- If using custom namespaces, they must already exist and be labeled — see
  [[configuring-custom-namespaces-for-rhoai]] (do this *before* installing
  the Operator).
- On OpenShift 4.21+: the OLMv1 catalog Technology Preview is on by default
  and can redirect Operator installs (NFD, NVIDIA GPU Operator, etc.) to a
  `ClusterExtensions` page instead of the normal flow — see
  [[operator-install-redirects-to-clusterextensions]] if you hit this.
- If you use a cluster proxy, the Operator's proxy settings can be
  overridden (see OpenShift's "Overriding proxy settings of an Operator" —
  not ingested into this wiki).

## In a disconnected environment

The disconnected-environment install guide covers the same Operator install
procedure below almost verbatim, with these differences layered in:

- **Internet access applies to the mirroring machine, not the cluster.**
  The disconnected guide reframes the domain-access precondition above as
  "Internet access on the mirroring machine": the machine used to mirror
  images needs access to `cdn.redhat.com`, `subscription.rhn.redhat.com`,
  `registry.access.redhat.com`, `registry.redhat.io`, `quay.io` (and the
  NVIDIA domains only if building/pulling custom CUDA images) — the cluster
  itself does not need direct internet access.
- **Extra precondition: mirror images first.** Before installing the
  Operator, all required container images must be mirrored to a private
  registry — see [[mirroring-images-for-disconnected-install]] (a wholly
  new procedure with no connected-cluster equivalent).
- **After installing the cluster** (before installing the Operator), also
  configure the Cluster Samples Operator for a restricted network — see
  "Configuring Samples Operator for a restricted cluster" in the OpenShift
  docs (external, not ingested).
- **`Subscription.spec.source` differs.** On a connected cluster this
  targets the default `redhat-operators` catalog source. In a disconnected
  environment it must instead reference the `CatalogSource` generated by
  the mirroring procedure, named `cs-redhat-operator-index` by default:
  ```yaml
  spec:
    name: rhods-operator
    channel: <channel>
    source: cs-redhat-operator-index
    sourceNamespace: openshift-marketplace
    startingCSV: rhods-operator.x.y.z
  ```
- Everything else — namespace/OperatorGroup/Subscription creation via CLI,
  the web console install flow, channel/version/update-approval choices,
  and verification — is unchanged between the two guides.

## Steps — using the CLI

1. Log in as a cluster administrator:
   `$ oc login --token=<token> --server=<openshift_cluster_url>`
2. Create the operator namespace (skip if a custom one already exists):
   ```yaml
   apiVersion: v1
   kind: Namespace
   metadata:
     name: redhat-ods-operator
   ```
   `$ oc create -f rhods-operator-namespace.yaml`
3. Create an `OperatorGroup`:
   ```yaml
   apiVersion: operators.coreos.com/v1
   kind: OperatorGroup
   metadata:
     name: rhods-operator
     namespace: redhat-ods-operator
   ```
   `$ oc create -f rhods-operator-group.yaml`
4. Create a `Subscription`:
   ```yaml
   apiVersion: operators.coreos.com/v1alpha1
   kind: Subscription
   metadata:
     name: rhods-operator
     namespace: redhat-ods-operator
   spec:
     name: rhods-operator
     channel: <channel>            # fast, fast-x.y, stable, stable-x.y, eus-x.y, or alpha — see [[rhoai-operator-update-channels]]
     source: redhat-operators      # in a disconnected environment, use cs-redhat-operator-index instead — see "In a disconnected environment" above
     sourceNamespace: openshift-marketplace
     startingCSV: rhods-operator.x.y.z   # optional; omit for latest
   ```
   `$ oc create -f rhods-operator-subscription.yaml`

If using a custom operator namespace, replace `redhat-ods-operator`
throughout.

## Steps — using the web console

1. Log in to the web console as a cluster administrator.
2. **Operators** → **OperatorHub**, find **Red Hat OpenShift AI** (filter by
   keyword).
3. Click the tile → **Install**.
4. Select a **Channel** and **Version** (see
   [[rhoai-operator-update-channels]]).
5. **Installation mode**: only **All namespaces on the cluster** is
   available.
6. **Installed Namespace**: pick the recommended `redhat-ods-operator` or a
   pre-created custom namespace.
7. **Update approval**: **Automatic** (auto-upgrades through the channel to
   latest) or **Manual** (admin approves each sequential step).
8. Click **Install**.

## Verification

- Web console → Installed Operators (**Ecosystem → Installed Operators** on
  OCP 4.20+, **Operators → Installed Operators** on 4.19) → confirm status
  is **Succeeded** (may show **Installing** for several minutes first).
